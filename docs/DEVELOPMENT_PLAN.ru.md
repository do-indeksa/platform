# Do indeksa: план разработки MVP

Срез плана: 11 августа 2026 года. Основа решений -
`docs/PROJECT_INDEX.ru.md`.

## 1. Цель MVP

Пользователь без регистрации должен решить реальную по стилю FTN P1 задачу,
получить точную тренировочную обратную связь и перейти в короткий цикл
подготовки. После накопления данных платформа должна показать, какие области
слабые, что делать сегодня и как меняется результат полного пробника.

Успех MVP - работающий замкнутый цикл в pixel-perfect интерфейсе Figma:

`решение -> обратная связь -> попытка -> карта -> следующая тренировка -> пробник`

## 2. Принципы исполнения

- Реализовывать вертикальными срезами, каждый из которых можно проверить
  пользователем от начала до конца.
- Для каждого существующего screen node переносить Figma pixel-perfect; менять
  только подтвержденно ложные предметные данные без самостоятельной композиции.
- Не показывать несуществующие предметы, объемы контента и точность прогнозов.
- Разделять тренировочную проверку конечного ответа и официальное оценивание
  хода решения.
- Сохранять guest-first; авторизация нужна для синхронизации между устройствами,
  а не для первого результата.
- Контент проходит математическую проверку независимо от code review.
- Сербский текст задач является каноническим; интерфейс локализован на
  `sr-Latn`/`en`/`ru`. Будущие переводы контента должны оставаться версиями
  одного task ID и не дублировать answer/check/rubric.
- Автоматические и AI-проверки не переводят задачу в `verified` без отдельной
  maintainer review и не выдаются за официальное оценивание FTN.
- Доступность и mobile layout входят в Definition of Done каждого среза.
- Экран без Figma допускается только как tracked provisional skeleton и не
  считается завершенным визуально.

### Цель первых двух недель

За 1-2 недели целевой результат - не весь MVP ниже, а портфолио-уровень `v0.1`:

- актуальная доменная модель P1 без вымышленных экзаменов и чисел;
- трехъязычный responsive shell;
- завершенный цикл одной задачи с проверкой, подсказками, решением и попыткой;
- несколько безупречно оформленных маршрутов, visual regression и понятный
  README с архитектурой;
- deploy preview или production deploy, если инфраструктурный аудит не мешает
  качеству продукта.

Изначально диагностика, персональный план и пробник были следующими
вертикальными срезами; они вошли в portfolio checkpoint раньше плана.
AI-оценивание остается вне критического пути. Качество важнее формального срока.

coverage для error states и long Serbian copy, а также production rollout.
Analytics сознательно fail-closed до безопасного image.

## 3. Критический путь

### Срез 0. Продуктовая корректность и app shell

Приоритет: P0. Оценка: 2-4 инженерных дня.

Работы:

- заменить в продуктовых константах 180 минут на актуальные 4 часа;
- перестать показывать boolean-самооценку как официальный балл 0/6;
- развести `topic` и `examPosition`, учесть перестановку областей 3/4;
- зафиксировать versioned blueprint P1;
- воспроизвести canonical Figma tokens, typography, buttons, inputs и app shell
  без самостоятельно добавленных navigation blocks;
- сделать desktop/tablet/mobile navigation без переполнения;
- оставить в тренировочном UI только FTN P1; удалить Physics/P2 и не показывать
  P3 как уровень P1;
- ввести locale-routing и переключатель `sr-Latn`/`en`/`ru`, сохранив сербский
  каноническим языком task-контента;
- добавить проверку фактических чисел и дат в макетных данных.

Готово, когда:

- нигде в UI P1 не описан как 180-минутный экзамен;
- никакой экран не показывает больше 60 экзаменационных баллов;
- на ширинах 360, 768 и 1440 px нет горизонтального переполнения и наложений;
- blueprint-тест подтверждает 10 позиций и допустимые темы;
- shell и навигация имеют полные версии на `sr-Latn`, `en` и `ru`, а отсутствие
  перевода task-контента дает явный сербский fallback без смешивания языков.

### Срез 1. Главный учебный цикл одной задачи

Приоритет: P0. Оценка: 5-7 инженерных дней.

Работы:

- воспроизвести Figma Solution/Tasks pixel-perfect, подставив реальные области
  FTN в существующие component slots;
- сделать список задач с фильтром по области, сложности и статусу прохождения;
- сохранить машинную проверку, две подсказки и полный разбор;
- добавить типичную ошибку, похожую следующую задачу и `Prijavi grešku`;
- измерять ответ, активное время, результат по частям и уровень помощи;
- добавить живую задачу на landing и CTA без регистрации;
- после первого результата предлагать сохранить прогресс, не блокируя переход.

Готово, когда:

- пользователь проходит полный цикл задачи на mobile и desktop;
- эквивалентные математические ответы проверяются тестами;
- повторная попытка и просмотр решения записываются без двойного счета;
- после ответа всегда есть одно понятное следующее действие;
- жалоба на ошибку содержит task ID и не требует ручного копирования текста.

### Срез 2. Данные прогресса и короткая диагностика

Приоритет: P0. Оценка: 5-8 инженерных дней.

Работы:

- ввести сущности `run` и расширенный `attempt` в GraphQL schema/Postgres;
- мигрировать local-first хранение без потери старых boolean-попыток;
- сделать диагностику отдельным blueprint, а не случайным полным вариантом;
- собирать ответы и время, поддержать паузу/продолжение;
- автоматически проверять только те части, для которых есть надежный checker;
- показать карту покрытия, уверенность результата и области без достаточных
  данных;
- не конвертировать короткую диагностику в обещание официального балла P1.

Рекомендуемая модель onboarding:

- одна живая задача дает мгновенную ценность;
- короткая диагностика строит предварительную карту;
- полный пробник позже измеряет экзаменационную выносливость и rubric-score.

Точное число задач и лимит времени короткой диагностики нужно откалибровать на
пилоте. До этого числа в Figma не должны выглядеть научно подтвержденными.

Готово, когда:

- незавершенную диагностику можно безопасно продолжить;
- карта явно различает `нет данных`, `предварительно` и устойчивый уровень;
- результат воспроизводим из сохраненного run;
- guest-данные после входа корректно объединяются с серверными.

### Срез 3. Персональная тренировка и план на сегодня

Приоритет: P0. Оценка: 5-7 инженерных дней.

Сначала нужен простой детерминированный алгоритм, а не сложная рекомендательная
система. Он учитывает:

- недавнюю точность;
- зависимость от подсказок;
- пропуски и ошибки;
- время решения;
- давность последней практики;
- отсутствие минимального числа наблюдений.

Работы:

- сформировать набор на 15-25 минут из 3-5 задач;
- приоритизировать слабые и непроверенные области;
- добавить повтор ошибок и постепенное повышение сложности;
- воспроизвести Figma Study Plan pixel-perfect, заполнив его widgets
  объяснимыми следующими действиями вместо фиктивных часов и прогнозов;
- объяснять причину каждой рекомендации одной короткой фразой;
- пересчитывать план после каждой значимой сессии.

Готово, когда:

- одинаковое состояние пользователя дает одинаковый план;
- алгоритм покрыт таблицей сценариев и unit-тестами;
- нет фиктивных оценок "осталось N часов";
- завершение набора меняет карту и следующую рекомендацию.

### Срез 4. Полный пробный P1

Приоритет: P0. Оценка: 7-10 инженерных дней.

Работы:

- собирать вариант по versioned P1 blueprint;
- установить актуальный лимит 4 часа;
- дать autosave, навигацию, пропуск и восстановление после reload;
- скрыть подсказки, решения и мгновенную правильность до сдачи;
- после сдачи провести пользователя по rubric каждой части;
- хранить earned/max points, а не только `correct`;
- показать 0-60, результат по областям, время и следующий weak-topic set;
- маркировать полностью автоматический результат как оценку тренажера, если
  ход решения не проверен.

Готово, когда:

- reload и краткий offline не уничтожают экзамен;
- таймер устойчив к sleep/background и опирается на абсолютный deadline;
- результат нельзя превысить выше 60;
- частичный балл восстанавливается из сохраненной rubric-оценки;
- завершенный пробник появляется в общей истории и влияет на план.

Состояние на 11 августа: lifecycle реализован. Точный конечный ответ остается
автоматической попыткой на 6 баллов; для неверных и пропущенных ответов с
проверенной rubric пользователь отдельно оценивает записанный на бумаге ход
решения в диапазоне 0-5. Эти баллы маркируются как самооценка, переживают reload
и cross-device recovery и не выдаются за официальный результат FTN. Pilot
rubric покрывает все 30 независимо проверенных задач в десяти темах.

### Срез 5. История, ошибки и кабинет

Приоритет: P1. Оценка: 5-7 инженерных дней.

Работы:

- воспроизвести Figma Cabinet/History pixel-perfect и заполнить предусмотренные
  states фактическими данными;
- сгруппировать отдельные попытки, тренировки, диагностики и пробники;
- добавить фильтры по типу, области и периоду;
- сделать тетрадь ошибок с повтором задачи или похожего типа;
- показать зависимость результата от подсказок и времени;
- оставить на кабинете одно основное действие `Nastavi`.

Готово, когда:

- любая цифра кабинета раскрывается до конкретных попыток;
- историю можно восстановить после входа на другом устройстве;
- удаленные/измененные задачи не ломают старый run;
- пустые, loading, degraded и error states реализованы.

### Срез 6. Справочник FTN и калькулятор

Приоритет: P1. Оценка: 5-8 инженерных дней.

Работы:

- превратить `cutoffs.yaml` в проверяемый источник с годом и официальной
  ссылкой;
- добавить каталог программ FTN, тип экзамена, квоты и понятное описание;
- поддержать до пяти желаний, не имитируя официальный сервис подачи;
- показать диапазоны прошлых проходных баллов с предупреждением, что это не
  гарантия;
- определить процесс ежегодной актуализации данных.

Готово, когда:

- все изменяемые числа имеют год, источник и дату проверки;
- калькулятор покрыт граничными тестами 0/40/60/100;
- устаревшие данные явно маркируются;
- продукт не обещает поступление по историческому cutoff.

## 4. Контентный поток

Текущие 30 задач подходят для портфолио-preview и проверки механики, но не для
обещания устойчивой диагностики и разнообразных пробников. Контент идет
параллельно разработке.

Предлагаемый launch-gate:

- минимум 10 проверенных авторских задач на каждую рабочую область;
- отдельный набор для диагностики, не пересекающийся с первой тренировкой;
- минимум несколько полных blueprint-совместимых пробников;
- у каждой задачи есть решение, две ступени подсказок, checker или явная
  маркировка ручной проверки, типичная ошибка и reviewer status;
- автоматическая проверка проходит property/fixture tests на эквивалентных и
  ошибочных ответах.

Число 10 на область является инженерным launch-gate против немедленных
повторов, а не доказанным педагогическим минимумом. После пилота его нужно
пересмотреть по данным.

Автоматизированный quality gate до появления преподавателя:

- schema и source/provenance validation;
- независимые fixtures и property tests для checker;
- числовая подстановка в промежуточные и конечные формулы, где это возможно;
- отдельный audit статусов: `review` не переименовывается в `verified` только
  потому, что тесты зеленые;
- машинный перевод проходит проверку терминологии, LaTeX и неизменности чисел,
  но остается переводом канонического сербского текста.

AI-grading не входит в критический путь `v0.1`. Позже он реализуется как
provider-neutral `ai_assisted` strategy: модель получает условие, заготовленное
решение и явную rubric, возвращает структурированные баллы с доказательствами и
confidence. Перед показом пользователям каждый провайдер сравнивается на
фиксированном gold-наборе; низкая уверенность приводит к self-check, а не к
выдуманному баллу.

## 5. Предлагаемые контракты данных

### Task content

```yaml
id: string
topic: string
eligiblePositions: [3, 4]
difficulty: 1..4
origin: authored | official-reference
source:
  title: string
  url: string?
  year: number?
status: draft | review | verified
parts:
  - id: string
    maxPoints: number
    check: object?
commonMistake: markdown
relatedTaskIds: [string]
```

### API domain

```text
Run
  id, userId?, kind, status, blueprintVersion
  startedAt, submittedAt?, deadlineAt?, durationMs?

RunItem
  runId, taskId, ordinal, examPosition
  answer, outcome, earnedPoints?, maxPoints?, gradingKind

Attempt
  id, userId?, runId?, taskId, mode
  startedAt, submittedAt, activeDurationMs
  answer, outcome, helpLevel, gradingKind
  earnedPoints?, maxPoints?

GradingKind
  auto | rubric_self | ai_assisted | human
```

Перед миграцией нужен отдельный ADR: хранить ли `RunItem` отдельно или считать
attempt частью run. В любом варианте завершенная история должна быть
восстановима без текущей версии контентного файла.

## 6. Тестовая стратегия

- Unit: answer equivalence, scoring rubric, mastery, recommendation rules,
  blueprint generation, cutoff formulas.
- Contract: GraphQL schema/operation validation, guest-to-user merge,
  идемпотентные mutations запуска и попытки.
- Integration: start/resume/finish diagnostic and simulation.
- Browser: основные сценарии на 360x800, 768x1024 и 1440x900.
- Visual: 21 канонический Linux screenshot для первого viewport overview, task,
  empty plan, empty history, diagnostic result, rubric review и simulation
  result на 360x800, 768x1024 и 1440x900; следующим слоем покрывать ошибки и
  long Serbian copy.
- Content: schema, math fixtures, сумма rubric points, ссылки и статус review.

## 7. Порядок релизов

| Релиз | Состав    | Пользовательская ценность                          |
| ----- | --------- | -------------------------------------------------- |
| R0    | срез 0    | продукт больше не сообщает неверный формат         |
| R1    | срез 1    | portfolio v0.1: можно качественно решить задачу    |
| R2    | срезы 2-3 | появляется измеримый персональный цикл             |
| R3    | срез 4    | доступен правдоподобный полный пробник             |
| R4    | срез 5    | прогресс и ошибки становятся повторяемым процессом |
| R5    | срез 6    | подготовка связывается с выбором программы FTN     |

R0-R1 можно целиться закончить за 1-2 недели интенсивной работы. Для одного
инженера с готовым дизайном полный подготовительный MVP до R4, без учета темпа
математического review, остается оценкой в 6-8 инженерных недель. Это оценка
порядка величины, а не календарное обещание; контент является независимым
критическим путем.

## 8. Что не делать до R4

- не придумывать собственную композицию для экранов, уже существующих в Figma;
- не показывать несуществующие Physics/P2 и не открывать P3-P8 как тренажеры;
- не строить AI-чат, marketplace преподавателей или social mechanics;
- не обещать вероятность поступления без калиброванной модели;
- не делать сложный drag-and-drop конструктор раньше guided weak-topic set;
- не расширять на другие университеты до подтвержденного цикла FTN P1;
- не коммитить OCR и оригинальные защищенные материалы.

## 9. Следующий исполнимый пакет

Работа продолжается теми же небольшими независимыми PR:

1. После готового public landing пересобрать `/cabinet`, Solution и остальные
   существующие routes по точным Figma nodes небольшими UI PR; принимать новые
   visual baselines только после overlay-review.
2. Расширять verified-банк за пределы текущих 30 задач и обновлять независимый
   review-record при каждом изменении полной темы.
